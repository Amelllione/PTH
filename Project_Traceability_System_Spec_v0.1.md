# Спецификация системы знаний и трассировки проекта

**Рабочее название:** Project Traceability Hub (PTH).  
**Версия:** 0.1.  
**Дата:** 2026-10-04.  
**Статус:** проект для обсуждения; документ ещё не принят пользователем.  
**Назначение:** исходная спецификация для разработки API-сервера, UI, MCP-интерфейса, набора скиллов Claude Code и интеграции с Git.

## 1. Основания и границы

### 1.1. Подтверждённые пожелания

1. Требования и решения имеют неизменяемые ID и образуют реестр связанных сущностей.
2. API-сервер входит в первую версию и обслуживает создание и все допустимые изменения данных.
3. Работа с сервисом через Claude обеспечивается скиллами.
4. UI позволяет просматривать и анализировать артефакты, редактировать их и видеть последствия изменений.
5. Пользователь обсуждает продукт с ИИ вне сервиса, получает драфт спецификации, корректирует и принимает его. Затем Claude раскладывает принятый текст в систему.
6. Дальнейшие изменения выполняются через скиллы или UI.
7. Сервис является единой точкой получения знаний о требованиях, коде и ключевых решениях проекта для ИИ.
8. Нужна трассировка до конкретных коммитов кода.
9. Спецификация строится от User Story к ФТ.
10. Из связанных требований должна формироваться ПСИ и другие полезные проектные представления.

### 1.2. Предлагаемые решения

Остальные решения этого документа — предложения, а не уже согласованные ограничения. Чтобы разработка могла начаться после принятия документа, для спорных вариантов выбран конкретный рабочий вариант; альтернативы и открытые вопросы указаны в разделе 20.

Предлагается начать с self-hosted веб-сервиса для одного владельца и нескольких проектов. При этом модель сразу различает пользователей, сервисные аккаунты и проектные права. Реестры сущностей, изменения, UI, REST API, MCP, импорт принятой спеки и Git-трассировка входят в первый пригодный к использованию релиз.

Основной клиент ИИ первой версии — Claude Code. Для Claude Desktop/claude.ai необходима отдельная проверка возможностей подключения в конкретной среде. Наличие SKILL.md само по себе не предоставляет сетевой доступ или права к сервису.

### 1.3. Источник истины

После импорта каноническое состояние требований и решений находится в серверном реестре. Первоначальная принятая спецификация сохраняется как неизменяемый источник. Экспорт БТ/ТЗ — представление состояния реестра на заданной baseline.

Исходный код остаётся в Git. Сервис хранит версии, ссылки, коммиты и проверяемые сведения о коде, а не заменяет репозиторий. Для ИИ сервис — единая точка получения контекста; физически исходные данные могут находиться в реестре, Git и хранилище результатов проверок.

Правка экспортированного документа не изменяет реестр автоматически. Пользователь явно передаёт новую редакцию на импорт; система строит diff и ChangeSet. Это предотвращает независимое расхождение двух источников истины.

### 1.4. Термины

| Термин | Определение |
| --- | --- |
| Artifact | Сущность проектного знания: US, ФТ, НФТ, ADR, компонент, проверка и т. п. |
| ArtifactRevision | Неизменяемая редакция содержимого Artifact |
| Relation | Типизированная направленная связь между Artifact |
| RelationRevision | Неизменяемая редакция связи, её статуса и основания |
| ChangeSet | Согласованный набор предлагаемых изменений |
| Baseline | Неизменяемый снимок конкретных редакций артефактов, связей и Git-состояния |
| ContextBundle | Версионированный пакет контекста, переданный ИИ для задачи |
| ImpactAnalysis | Расчёт потенциальных последствий ChangeSet |
| Suspect / needs_review | Связь или подтверждение требует перепроверки после изменения основания |
| Evidence | Свидетельство выполнения проверки на конкретной версии и в заданных условиях |
| Finding | Результат проверки: ошибка, предупреждение или рекомендация |
| SourceDocument | Неизменяемая редакция исходного документа |
| Coverage obligation | Применимая обязанность покрытия, например наличие теста для ФТ |
| ПСИ | Программа и методика испытаний; для проекта может включать приёмосдаточные испытания |

### 1.5. Принципы

- ID выдаёт сервер. ИИ не придумывает канонические ID.
- Все пользовательские изменения идут через доменный API. UI, MCP и CLI используют одни правила.
- Тексты ИИ, гипотезы, подтверждённые решения и результаты тестов различаются.
- Отсутствие ошибок проверки не означает выполнение всех требований.
- Анализ влияния объясняет путь и причину попадания объекта в результат.
- Сначала явные связи и воспроизводимые проверки, затем интеллектуальные рекомендации.
- Просмотр последствий доступен до применения правок.
- Права и политика применения проверяются сервером; инструкции скилла их не заменяют.
- Принятая внешняя спека и статус реализации её требований — разные состояния.
- Обязательные ограничения не теряются при ограничении объёма контекста ИИ.

## 2. Роли и сценарии

### 2.1. Роли

| Роль | Основные задачи |
| --- | --- |
| Владелец продукта / проекта | Принимает исходную спецификацию, контролирует полноту и изменения |
| Аналитик | Декомпозирует БТ/US/ФТ/НФТ, устраняет пробелы и противоречия |
| Архитектор | Ведёт ADR, компоненты, контракты и архитектурное покрытие |
| Разработчик | Получает контекст, реализует требования, связывает код и коммиты |
| QA / приёмщик | Создаёт проверки и ПСИ, фиксирует результаты |
| Claude / другой ИИ | Действует от сервисного аккаунта с определёнными правами |
| CI / Git-коннектор | Передаёт коммиты, проверки и технические свидетельства |
| Администратор | Управляет доступом, интеграциями, схемами и восстановлением |

Один человек может совмещать все человеческие роли. Профессия не равна permission-role: права задаются отдельно. ИИ не получает права владельца автоматически.

### 2.2. Сквозной основной сценарий

1. Пользователь обсуждает будущий продукт с ИИ в любом доступном чате.
2. Пользователь получает и корректирует текст спецификации.
3. Пользователь явно принимает конкретную редакцию текста.
4. Claude получает текст и указание импортировать его в выбранный проект.
5. Скилл создаёт SourceDocument, ImportSession и черновой ChangeSet.
6. Claude извлекает сущности, сопоставляет существующие ID, предлагает связи и сохраняет основания.
7. Сервер проверяет модель; Claude сообщает о пропусках, неоднозначностях и конфликтующих ID.
8. После разрешения блокирующих вопросов ChangeSet применяется в рамках ранее предоставленной политики. Повторное ручное подтверждение точной раскладки принятого текста не обязательно.
9. Пользователь видит реестр, исходные цитаты, граф и отчёт импорта.
10. При новой задаче Claude запрашивает ContextBundle, реализует изменения и связывает их с задачей, требованиями и коммитами.
11. При изменении требования UI/скилл показывает diff, влияние и требуемые перепроверки.
12. Проверки и ПСИ строятся из принятого состояния реестра; результаты привязаны к коду и baseline.

## 5. Модель данных и неизменяемая идентичность

### 5.1. Идентификаторы

- entity_uid: непрозрачный UUID, глобально уникальный.
- display_id: например DEMO-FR-000042; уникален в системе благодаря неизменяемому project_key.
- revision_uid: отдельный UUID конкретной редакции; revision_number монотонен в пределах сущности.
- relation_uid и relation_revision_uid: аналогичная модель для связи.
- revision не включается в постоянный display_id; deep link может явно фиксировать revision.
- seq выдаётся транзакционно; пропуски допустимы. Зарезервированный или удалённый ID не используется повторно.
- project_key нельзя менять после создания. display_name проекта и title сущности менять можно.
- Тип сущности после создания неизменяем. Исправление типа: новая сущность + replaces + mapping, чтобы префикс и история не расходились.
- Один Artifact может находиться в нескольких документах/представлениях; location не участвует в identity.
- Дубликаты display_id и alias namespace сервер отклоняет; одинаковые title допустимы.

При импорте временные client_ref, например tmp:fr:section-4.2:01, действуют только внутри ImportSession/ChangeSet. Apply возвращает client_ref→entity_uid/display_id. Temp ref не является каноническим ID.

Текущие указатели Artifact/Relation изменяемы транзакционно; содержимое Revision неизменяемо. Состояния jobs и delivery — операционные, не являются редактированием прошлого проектного знания.

### 5.4. Независимые состояния

**Artifact lifecycle:** draft → proposed → agreed → deprecated → archived. allowed transitions заданы типом. Архивирование не стирает данные; восстановление создаёт новую revision.

**ADR decision_status:** proposed, accepted, rejected, superseded. Связь supersedes обязательна для замещённого решения; old ADR сохраняется.

**Relation status:** proposed, confirmed, rejected; freshness отдельно: current, needs_review, orphaned. Не следует кодировать все сочетания в один enum.

**Реализация и проверка:** specified, designed, implementation_claimed, implementation_observed, verified, accepted — вычисляемые аспекты, а не линейный статус Artifact. Требование может иметь проектирование, но не иметь актуальной проверки; accepted на старой baseline не переносится на новую.

**Finding:** open, acknowledged, resolved, dismissed. Dismissal требует причины и прав; при изменении проверяемого основания finding может открыться заново.

**Evidence:** immutable result: pass, fail, blocked, inconclusive; актуальность и доверие — отдельные вычисляемые атрибуты. ИИ-резюме не заменяет raw result.

## 6. Семантика связей и правила влияния

### 6.1. Каталог связей

Направление в таблице каноническое. Обратный label вычисляется для отображения, вторая зеркальная запись не создаётся.

| Тип | Направление | Смысл | Изменение какого конца требует пересмотра |
| --- | --- | --- | --- |
| refines | Детальное требование/US → исходное BR/US/требование | Декомпозиция/уточнение | Изменение исходного → детальные; изменение детального → кандидат проверки покрытия исходного |
| satisfies | Детальное требование/решение → требование | Заявленное покрытие | Изменение требования → покрывающее; изменение покрывающего → повторная оценка покрытия |
| motivates | Требование/риск → ADR | Основание решения | Изменение основания → ADR |
| constrains | НФТ/CON → CMP/INT/ADR/TASK | Ограничивает допустимые решения | Изменение ограничения → ограничиваемые |
| implements | CMP/CODE/COMMIT → FR/NFR/US/TASK | Область реализации | Изменение требования → реализация требует review; изменение кода → проверки требования |
| realizes | CODE → CMP/INT | Реализация компонента | Изменение кода → возможное изменение описания компонента |
| verifies | TEST → требование/критерий | Способ проверки | Изменение требования/критерия → TEST; изменение TEST → оценка покрытия |
| depends_on | Любой допустимый Artifact → зависимость | Семантическая зависимость | Изменение зависимости → зависимые |
| supersedes | Новый объект → старый | Замещение | Не распространяет функциональное влияние без дополнительной смысловой связи |
| derived_from | Производный объект → источник/основание | Происхождение | Изменение основания → кандидат review производного |
| includes | PSI/PLAN/RELEASE → включённый объект | Состав | Изменение включённого → обновление представления/проверка состава |
| addresses | TASK/PLAN → требование/ISSUE/RISK | Область работы | Изменение адресуемого → план/задача |
| conflicts_with | Artifact → Artifact | Зафиксированное противоречие | Обе стороны; отображается симметрично, хранится с нормализованным порядком uid |
| related_to | Artifact → Artifact | Навигационная связь | По умолчанию влияние не распространяет |

Links Evidence→TEST/revisions, AgentRun→ContextBundle и Commit→CodeReference реализуются строгими отдельными FK/manifest-полями, а не произвольными семантическими связями. В графе они отображаются как технические рёбра.

### 6.2. Валидация графа

- dangling links, чужой проект, недоступный объект и self-link отклоняются.
- Для refines и supersedes запрещены циклы. Для depends_on цикл — finding, если policy не запрещает его; произвольный граф не обязан быть DAG.
- По паре endpoints/type/scope запрещены дубли активной confirmed-связи.
- Proposed-связь может сосуществовать с альтернативной proposed; подтверждение требует разрешения коллизии.
- У refines/satisfies могут быть несколько родителей. Один НФТ может ограничивать множество компонентов.
- Relation basis содержит явную ссылку/цитату либо объяснение человека. ИИ confidence не является основанием сам по себе.
- Coverage учитывает direction, scope, accepted endpoint revisions и freshness.

### 6.3. Applicability ограничений

Ограничение имеет applicability: project-wide, component set, bounded_context, artifact types, environment, release scope. Scope задан структурированно; v1 поддерживает AND/OR по разрешённым атрибутам без исполнения пользовательского кода.

Для нового компонента контекст включает project-wide ограничения и ограничения подходящего bounded_context даже при отсутствии constrains. Система предлагает недостающие явные связи. Удаление constrains не отменяет применимость project-wide ограничения.

### 6.4. Алгоритм ImpactAnalysis

1. Зафиксировать base snapshot, proposed ChangeSet и rule_set_version.
2. Вычислить field-level diff и классифицировать изменения: text/editorial, behavior, metric/threshold, scope, lifecycle, relation, code.
3. Собрать direct impacts по правилам. Редакторский diff снижает severity только при детерминированно безопасных изменениях; смысловая классификация ИИ — рекомендация.
4. Обойти разрешённые правилами направления до budget. visited key включает node, rule и direction; графовые циклы не зацикливают расчёт.
5. Добавить применимые ограничения и obligations; не ограничиваться соседями изменённого узла.
6. Сформировать ImpactItem для каждой затронутой revision со всеми существенными путями, certainty и action.
7. Рассчитать coverage delta, новые gaps и возможные conflicts.
8. Вернуть complete/truncated/pending и точные лимиты. Частичный анализ не отображается как полный.
9. При apply записать invalidation markers/события в той же транзакции, что новые revisions. Полный обход может выполняться worker.
10. До завершения worker все потенциально затронутые derived confirmations имеют conservative pending status. Зелёный readiness не возвращается на непроанализированном новом graph_revision.

Выделяются certainty: explicit (явная структурная связь), inferred (предложение ИИ), unknown. Direct/transitive — отдельный атрибут, не степень уверенности.

Пример: изменение порога NFR → constrains CMP → realizes CODE → связанные commits/test obligations. Коммит прошлого кода immutable; меняется актуальность заявления, что этот код выполняет текущую редакцию НФТ.

### 6.5. Перепроверка и распространение

ReviewResolution хранит against_artifact_revisions и against_relation_revision. Снятие needs_review на одной связи не очищает весь граф. По ветви можно остановить дальнейший review только явным обоснованием «изменение не влияет» с фиксированными редакциями.

Большой проект требует server pagination и группировки по компоненту/роли. Уведомление по каждой транзитивной связи отдельно не обязательно; inbox агрегирует одну причину изменения с её объектами.

## 7. ChangeSet, согласованность и автономность

### 7.1. Состав ChangeSet

Изменение включает title/reason, base_graph_revision, actor, on_behalf_of, channel, context_bundle_uid, source refs, operations, expected_revisions, draft_revision и policy_mode.

Операции: create_artifact, revise_artifact, transition_artifact, archive_artifact, create/revise/archive_relation, bind_source, resolve_finding, resolve_review, grant_waiver, register/link_commit, attach_evidence, create_baseline, update_project_policy. Строгие сущности Commit/Evidence/Source имеют специализированные операции; сервер не допускает изменения их прошлого содержимого.

CRUD — это доменные команды. «Любые изменения модели через API» не означает произвольную запись в таблицы или отключение invariant checks.

### 7.2. Состояния

draft → validating → ready → applied; отдельно blocked, cancelled. awaiting_review применяется только при configured policy. Failed job не переводит применённый ChangeSet обратно в draft.

Изменение operations увеличивает draft_revision и инвалидирует validation, impact и review decisions прежней редакции. Apply допускается только для exact hash проверенного набора.

### 7.3. Транзакция apply

В одной DB-транзакции:

1. Проверить authorization и Idempotency-Key.
2. Заблокировать строку проекта и проверить base_graph_revision/expected revisions.
3. Проверить schema, relation constraints, policy и действительность review decisions.
4. Создать revisions, current pointers, mappings и необходимые conservative invalidation markers.
5. Записать AuditEvent и OutboxEvent.
6. Увеличить graph_revision; mark ChangeSet applied.
7. Commit; вернуть result manifest.

Модель graph_revision проекта в v1 оптимистично сериализует apply и может давать конфликт даже при независимых правках. Это сознательный компромисс первого релиза. Rebase API обновляет base и повторяет проверки; auto-merge допускается только для непересекающихся полей без изменения смыслового контекста и с повторным impact.

External Git, LLM и object storage не включаются в DB-транзакцию. Bytes предварительно загружаются и проверяются; операция ссылается на durable object. Недопривязанные uploads удаляются по retention. Git links принимаются verified либо явно pending; pending не считается подтверждённой трассировкой.

### 7.4. Policy автономности

| Класс операции | Предлагаемый режим по умолчанию |
| --- | --- |
| Read/search/context/impact | Без дополнительного согласования в пределах доступа |
| Черновики, findings, proposed links | Разрешены сервисному аккаунту |
| Точная раскладка принятой спеки | Разрешена в импортном scope; acceptance_basis сохранён |
| Изменения реализации в пределах согласованной задачи | Разрешены delegated capability, с тестами/аудитом |
| Новое бизнес-требование, изменение принятых ограничений, принятие ADR | Требуют полномочия человека либо явной заранее заданной делегации |
| Результат CI | Разрешён trusted integration principal |
| Baseline/release acceptance/waiver | По capability, не автоматически для любого ИИ |
| Права, токены, retention | Только admin |

Человек может разрешить автономное выполнение заранее по проекту, типу операции, объектам и сроку. Система не требует повторного подтверждения каждого API-вызова. Подтверждение в чате записывается как указание владельца с происхождением; его нельзя выдавать за криптографически доказанную подпись человека.

### 7.5. Идемпотентность и компенсация

Idempotency-Key scoped к principal/project/operation. Для одинакового key+payload hash возвращается исходный результат. Другой payload с тем же key → 409 IDEMPOTENCY_CONFLICT. Хранятся результат и status; retry после network timeout безопасен.

Компенсация создаёт новые revisions с restore content; если затронутый объект изменён позже, сервер требует rebase/resolve. Исторический commit, Evidence и audit не переписываются.

## 8. Импорт принятой спецификации

### 8.1. Разделение ответственности

Сервер не обязан иметь собственную LLM: Claude выполняет extraction/reasoning через скилл; сервер хранит, валидирует, рассчитывает явные связи и применяет изменения. Это позволяет использовать другие модели без замены ядра.

Задачи сервера: ingestion, fragment manifest, schemas, candidate API, idempotency, deterministic validation, mapping IDs, coverage report, apply.

Задачи Claude: выделить сущности, сформулировать extraction candidates, предложить связи и semantic findings. Предложение новых требований выходит за «точную раскладку».

### 8.2. ImportSession

P0 принимает UTF-8 text/Markdown, JSON interchange и bundle с attachments. DOCX/PDF extraction — P1 отдельный адаптер; их не следует молча включать в стоимость первой версии.

Chunk manifest строится сервером по структуре; locator хранит section path и offsets в каноническом extracted text плюс exact_quote/hash. Для исходного Markdown сохраняются bytes и соответствие offsets. Размеры определяются в Unicode code points с явной convention, не «символами» неопределённой кодировки.

Для повторяемости extraction chunk_id стабилен для source_revision. Candidate key включает session_uid, chunk_uid и client_ref. Пересекающиеся chunks дедуплицируются по source_binding и явному resolution, а не только title.

### 8.3. Последовательность

1. source upload → hash verification → record accepted instruction.
2. create ImportSession → получить schema/rules/chunks/existing alias mappings.
3. По частям: extract entities/relations/issues → stage candidates.
4. Установить disposition фрагментов: extracted, supporting_context, open_issue, excluded_with_reason.
5. Validate IDs/schemas/links/coverage → вернуть findings и temporary→canonical reservations.
6. Resolve blocking ambiguities; scope accepted source и inferred additions отображаются отдельно.
7. Preview source map, registry delta и impact.
8. Apply accepted extraction ChangeSet согласно import capability.
9. Создать initial baseline если actor имеет отдельное право; иначе показать возможность.
10. Выдать отчёт: counts, mappings, unresolved items, invented candidates, source gaps.

Система допускает частично импортированный большой документ, но не маркирует весь источник как fully imported, пока manifest не закрыт. Применение небольших batches явно отражается в отчёте; исходная baseline первого импорта создаётся после завершения согласованного объёма.

### 8.4. Повторный импорт и расхождение

Match precedence: explicit canonical ID → existing namespaced alias → explicit user mapping → candidate fuzzy matches. Удаление пункта из документа не означает автоматическое архивирование: сначала проверяется scope импорта и полнота нового документа.

Если документ экспортирован раньше текущего graph_revision, сервер показывает three-way comparison: export baseline, current registry, imported revision. Молчаливый last-write-wins запрещён.

Метрика «доля обработанных фрагментов» измеряет техническое покрытие источника, не семантическую полноту требований. Параграф может получить disposition и всё ещё содержать пропущенное обязательство; это проверяется дополнительным semantic review.

## 9. API-сервер

### 9.1. Общий контракт

REST base: /api/v1. UTF-8 JSON; OpenAPI и JSON Schema входят в поставку. MCP — второй transport того же доменного контракта.

- Auth: user session для UI; scoped bearer token для сервисов. Tokens не передаются в URL.
- Все mutation commands: Idempotency-Key; actor определяется auth, а не произвольным полем тела.
- Редактирование drafts: If-Match draft ETag; apply: expected project/subject revisions.
- POST job/analysis/context creation: 201 для малого синхронного результата или 202 с job_uid/location.
- Чтение: cursor pagination, limit ≤200; graph endpoints имеют отдельные nodes/edges/path budgets.
- Read snapshot задаётся baseline_uid или graph_revision. Нельзя смешивать разные revisions без явного comparison mode.
- Query graph_revision обеспечивается snapshot manifest/consistent DB read; current не меняется посреди ответа.
- Response: data, meta {request_id, graph_revision, schema_version, completeness, next_cursor}; ошибки — problem details.
- UI, CLI, MCP не обращаются к БД напрямую. Worker использует application services с system principal; изменения имеют audit.
- Изменения проекта/ключей/интеграций тоже доступны через API, но имеют отдельные management commands.

        "attributes.threshold": {"operator": "<=", "value": 2, "unit": "s"}
      }
    },

### 9.5. Ошибки

| HTTP / code | Значение и действие клиента |
| --- | --- |
| 400 INVALID_COMMAND | Некорректная форма запроса |
| 401 AUTH_REQUIRED | Обновить auth; не повторять mutation без idempotency |
| 403 CAPABILITY_DENIED | Прав нет; скилл не обходит запрет |
| 404 NOT_FOUND | Объект отсутствует или недоступен; не раскрывать чужой проект |
| 409 REVISION_CONFLICT | Получить текущие revisions, rebase и повторно проанализировать |
| 409 IDENTITY_COLLISION | Разрешить mapping; не придумать новый alias молча |
| 409 IDEMPOTENCY_CONFLICT | Тот же key с иным payload |
| 409 ANALYSIS_OUTDATED | Обновить validation/impact для нового draft |
| 422 DOMAIN_VALIDATION | Показать field/operation findings |
| 422 MANDATORY_CONTEXT_INCOMPLETE | Расширить budget или разбить задачу |
| 423 REVIEW_REQUIRED | Политика требует решения уполномоченного principal |
| 429 RATE_LIMITED | Retry-After, bounded retry |
| 503 INTEGRATION_UNAVAILABLE | Job retry; не объявлять SHA verified |

Ответ ошибки содержит request_id, error code, message, subject refs и safe details; не включает token или полный confidential prompt.

### 9.6. Jobs и события

Job имеет input_hash/checkpoint. Retry допускается только для resumable job или создаёт новую попытку того же idempotent operation. Частично записанные extraction candidates сохраняются; apply не может быть «частично успешным».

Outbox delivery at-least-once; consumer дедуплицирует event_uid. Event payload содержит project, graph_revision, changed IDs, ChangeSet и job, не весь документ. Клиент запрашивает данные после уведомления.

## 10. Контекст для ИИ

### 10.1. ContextBundle contract

Запрос: project, purpose (import/design/implement/review/psi/answer), seed_ids или code refs, baseline/graph_revision, target refs, scope, budget, include kinds.

Ответ состоит из:

1. manifest revisions и bundle_hash;
2. цель и scope задачи;
3. обязательные требования/критерии и применимые ограничения;
4. актуальные ADR, альтернативы и superseded warnings;
5. компоненты, интерфейсы, термины;
6. кодовые anchors на фиксированных коммитах;
7. проверки, последние применимые evidence и coverage gaps;
8. открытые вопросы/conflicts/needs_review;
9. источники и точные ссылки;
10. omissions, truncation, estimated tokens и freshness.

Пакет хранит полные тексты переданных revisions либо immutable content-addressed refs, доступные при replay. Только список IDs без фактического содержимого недостаточен для воспроизведения работы ИИ.

### 10.2. Budget и актуальность

Приоритет: обязательные ограничения → целевые требования → решения → критерии проверки → интерфейсы/код → дополнительный контекст. Краткие summary всегда имеют links to full revisions.

Если обязательные сведения не помещаются, сервер возвращает incomplete bundle. ИИ должен получить дополнительные chunks или разбить задачу. Нельзя пометить контекст «полным» после молчаливого усечения.

В начале работы и перед apply/регистрацией реализации выполняется check-freshness. Exact replay остаётся доступен, но stale bundle нельзя выдавать за текущие знания. Commit link записывает requirement_revision, которую использовал разработчик.

### 10.3. Разделение знаний и инструкций

Текст документа и комментарии Git — данные проекта. Они не получают права системных инструкций. Скилл руководствуется своим workflow и серверными permissions. API не исполняет содержимое statement, locator, title или произвольные команды из источника.

Провайдер LLM/model/version/token usage — optional metadata AgentRun; ядро не требует конкретной модели. Автоматический поиск смысловых противоречий в P0 может запускаться Claude-скиллом; собственный LLM worker — P1.

### 11.3. Пример точного workflow pth-change

1. Resolve target IDs и запросить current revisions.
2. Сформировать task-scoped ContextBundle и прочитать обязательные ограничения.
3. Создать ChangeSet с base_graph_revision.
4. Добавить предложенные изменения и явные основания.
5. Получить impact; показать человеку либо вернуть агенту список связанных ADR/TEST/code refs.
6. Для связанных объектов: обновить, предложить review или обосновать отсутствие влияния.
7. Validate exact draft_revision; устранить structural blockers.
8. Если policy разрешает — apply; иначе оставить concrete reviewable draft и указать требуемое capability.
9. При 409 — rebase, новый impact, повторная validation; не повторять старый apply бесконечно.
10. Выдать applied manifest, оставшиеся review items и влияние на code/evidence.

### 11.4. CLAUDE.md и контроль

Короткий CLAUDE.md в подключённом репозитории содержит project_uid/API config reference, правило контекста перед задачей, обязательные ограничения, требования к trace manifest и ссылки на нужные скиллы. Secrets туда не помещаются.

Instructions/skills повышают вероятность соблюдения процесса, но не дают гарантии. Серверные invariants и CI checks обеспечивают запрет некорректных canonical writes. Git hook может быть обходным; обязательность достигается policy merge/CI, если настроена внешняя платформа.

Eval suite skill pack: точный импорт, неоднозначный НФТ, коллизия ID, stale bundle, изменённый ADR, interruption/retry, запрещённый apply, ложный SHA, commit без теста, неполная ПСИ. Expected behavior определяется PTH-AC сценариями.

### 12.3. Подсветка влияния

Рекомендуемые значения визуальных маркеров:

- «Изменяется»: объект входит в операции ChangeSet.
- «Требует перепроверки»: явное правило влияния или obsolete confirmation.
- «Возможно затронут»: inferred semantic candidate.
- «Нарушение»: воспроизводимая ошибка либо подтверждённое противоречие.
- «Данных недостаточно»: pending/truncated/no evidence.

Цвет всегда сопровождается текстом/иконкой. Требует перепроверки не обозначается как нарушенное требование. Sidebar причины показывает path, rule_id, affected fields и against revisions.

### 12.4. Редактирование

Autosave сохраняет только draft. Apply — отдельное действие, доступное по policy. Для небольшого изменения UI автоматически создаёт ChangeSet и запускает быстрый impact, но пользователь видит его ID.

Связь создаётся из карточки через type selector: допустимые target types, direction, scope и basis. Drag graph edge может быть альтернативным способом, но не единственным.

Разрешение review предлагает: обновить объект; проверить и подтвердить отсутствие влияния; заменить связь; принять scoped waiver. Ни одно действие не стирает историю.

409 открывает comparison current/base/proposed; введённый текст не теряется. UI не делает hidden overwrite.

### 12.5. Масштаб и доступность

Граф отображает локальное окружение, а не все тысячи узлов. Первая загрузка ≤200 nodes; дополнение по запросу. Подграф с truncation имеет явное сообщение и ссылку на полный табличный список.

Deep links: /projects/{key}/artifacts/{display_id}?revision=...; /projects/{key}/graph?focus={display_id}&depth=...; /projects/{key}/lost?priority=...; /changesets/{uid}; /commits/{uid}; /baselines/{uid}. Один и тот же ID можно копировать для Claude.

Tables virtualized, filters in URL, keyboard navigation, focus states, no color-only semantics. Источники и API-ошибки отображаются безопасно, без исполнения HTML из документа.

## 13. Трассировка до Git-коммитов

### 13.1. Обязательная цепочка

Целевая трасса: BR/US → FR/NFR → ADR/CMP/INT → TASK/PLAN → CODE/COMMIT → TEST/Evidence. Не каждый проект требует каждое звено; required obligations определяет policy.

Минимум для commit link: repository_uid, full_oid, requirement/task IDs и pinned revision, link_role, basis, issuer. Commit без pinned requirement revision считается неполной трассировкой.

Link roles: implements, refactors, fixes, tests, documents, reverts. Любое упоминание requirement ID не превращается в implements.

### 13.2. Способы подключения P0

1. Provider-neutral read-only Git adapter к настроенному remote.
2. CLI/CI передаёт SHA и signed/authenticated manifest; сервер проверяет объект при доступном adapter.
3. Без доступа к remote manifest получает pending verification. В UI это явно видно; readiness не считает его verified.

Полный Git hosting продукт не создаётся. Provider-specific PR UI/webhooks — P1; базовый sync и manifest API обязательны в P0. Доступ к remote ограничен заранее настроенным repository; arbitrary URL из запроса не скачивается.

### 13.3. Manifest

~~~json
{
  "repository_id": "repo-example",
  "object_format": "sha1",
  "commit_oid": "0123456789abcdef0123456789abcdef01234567",
  "change_set_id": "changeset-example",
  "context_bundle_id": "bundle-example",
  "links": [
    {
      "artifact_id": "DEMO-FR-000042",
      "artifact_revision_number": 3,
      "role": "implements",
      "code_refs": [
        {"path": "src/documents/access.py", "symbol": "get_document"}
      ]
    }
  ],
  "ci_run_ref": "provider-run-example"
}
~~~

SHA в примере фиктивный и не считается существующим. В реальном запросе Git-коннектор проверяет commit, tree, path и symbol/range. Symbol в P0 может быть advisory, если parser языка отсутствует; точная проверка path/blob обязательна. Line ranges относятся только к закреплённому commit.

### 13.4. Git trailers

Вариант сообщений коммита:

~~~text
Restrict document reads to the current tenant

Project-Artifact: DEMO-FR-000042@3
Project-Task: DEMO-TASK-000017
Project-Change: change-set-uuid
Project-Context: context-bundle-uuid
~~~

Парсер использует структурированные trailers. Они удобны для начального сопоставления, но являются claims автора. Сервер проверяет repo, IDs, revisions и присваивает trust/provenance; не извлекает доказательство корректности из commit message.

### 13.5. Изменения истории и актуальность

- Squash: итоговый SHA новый; links создаются заново с mapping source commits. Сопоставление по PR/manifest можно подтвердить; patch similarity только candidate.
- Rebase/cherry-pick: новый commit сохраняет explicit rewritten_from/cherry_picked_from; старый не заменяется.
- Revert: reverse change связывается с original commit; статус requirement implementation требует пересмотра.
- Rename/move: новая code ref на новом commit, old ref сохраняется.
- Deleted file: old anchor остаётся доступен на old commit; current code coverage получает gap.
- Force-push: ref observation меняется; baseline остаётся pinned. Artifact указывает, что коммит не reachable из текущего target.
- Несколько repo: baseline хранит exact oid каждого обязательного репозитория.

Сервис получает достижимость коммита из графа Git, не из времени коммита. Reachable original commit после revert не доказывает наличие его поведения: readiness учитывает linked reversal/change findings и актуальное Evidence.

### 13.6. Рабочий цикл разработки через Claude

1. Получить TASK + bundle и зафиксировать starting code heads.
2. Прочитать linked code; выполнить локальные изменения.
3. Подготовить tests/result manifest и зарегистрировать semantic/doc changes.
4. Перед commit повторно проверить bundle freshness. Если требования изменились, пересмотреть работу.
5. Создать commit только в рамках полученного разрешения на Git-работу; иначе показать diff и оставить prepared manifest.
6. После фактического commit зарегистрировать SHA, code refs и links через API.
7. CI/коннектор проверяет commit и results; unresolved discrepancies попадают в inbox.
8. При merge/squash повторно зарегистрировать фактический target commit и applicable results.

Если код принят, а регистрация сервиса временно недоступна, локальный manifest сохраняется в репозитории/CI artifact и повторяется с тем же idempotency key. Сервис показывает backlog; нельзя утверждать, что trace завершена.

## 14. Качество требований, свидетельства и ПСИ

### 14.1. Детерминированные правила P0

| VAL-TEST-01 | TEST покрывает criterion/revision и имеет expected outcome | Finding/block readiness |
| VAL-CODE-01 | Code ref существует на pinned commit | Block verified link |
| VAL-EVID-01 | Evidence точно соответствует TEST revision и baseline code | Block verified coverage |
| VAL-FRESH-01 | Confirmation не относится к устаревшим основаниям | needs_review |
| VAL-TRACE-01 | Обязательная цепь покрытия не разорвана | Gap, а не утверждение ошибки кода |
| VAL-CTX-01 | Mandatory context inclusion и bundle freshness | Block completeness claim |

Детерминированная проверка заполненности criterion не доказывает его качество. «Работает хорошо» может пройти JSON schema, но semantic review должен создать Finding о непроверяемости.

### 14.2. Семантические проверки

Скилл pth-requirements-review проверяет: несогласованную терминологию; скрытые requirements в ADR; противоречия БТ/ТЗ; взаимно несовместимые ограничения; неполную декомпозицию; безусловные утверждения при отсутствии данных; несоответствие реализации заявленной архитектуре.

Finding содержит subject revisions, source quotes, proposed contradiction, explanation, reviewer/model provenance и confidence. ИИ не переводит его в confirmed violation без предусмотренного review. Для точного структурного противоречия в формальных полях допустим deterministic rule.

### 14.3. Coverage

Единица покрытия — obligation, например (requirement_revision, criterion_key, scope, obligation_type). Типы: source, decomposition, design, implementation, verification_method, executed_verification, acceptance.

Обязательность зависит от requirement type и baseline scope. В denominator входят применимые обязательства; unknown applicability отображается отдельно и не исчезает из отчёта.

Coverage ratio = fulfilled applicable obligations / all applicable required obligations. Waived obligations выводятся отдельным числом; не повышают success ratio. Отчёт содержит scope, denominator, unresolved applicability и policy_version.

Различаются:

- design coverage: подтверждённые актуальные ADR/CMP/INT связи;
- code trace coverage: проверенные code/commit links, ещё без доказательства поведения;
- verification design coverage: TEST покрывает criterion;
- execution coverage: применимый результат выполненного TEST;
- acceptance coverage: уполномоченный акт принятия конкретной baseline.

Связь TEST→FR без покрытия всех обязательных критериев не даёт 100%. Failed test считается executed, но не passed. Blocked/inconclusive отдельны.

### 14.4. Evidence validity

Evidence применимо, если совпадают TEST revision, проверяемые requirement/criterion revisions, target code commits, среда/нагрузка и scope. Допустимость повторного использования Evidence для нового commit задаётся explicit equivalence review с причиной; timestamp не достаточен.

Результат после изменения current requirements остаётся валидным историческим свидетельством старой baseline, но не текущего состояния. Историческую baseline нельзя переписывать, массово превращая её старые pass в fail.

Evidence input идёт от authenticated issuer. Уровни доверия: human_recorded, agent_claimed, trusted_ci, independently_reviewed. Порог достаточности задаёт readiness policy.

### 14.5. Состав проекта ПСИ

Генератор создаёт PSI Artifact и Markdown export со следующими разделами:

1. Цель, объект и scope испытаний.
2. Основания: baseline, требования, решения и версии.
3. Комплектность системы, среды и тестовых данных.
4. Условия запуска, зависимости и порядок выполнения.
5. Матрица требование/критерий → метод → TestCase.
6. Методики: предусловия, вход, шаги, ожидаемое поведение, измерения.
7. Критерии успеха, остановки и повторения.
8. Форма фиксации результатов, attachments и ответственные.
9. Непокрытые требования, неопределённые параметры и исключения.
10. Правила принятия результатов.

Генератор сначала переиспользует согласованные TEST; затем предлагает новые draft tests для gaps. Он не создает «успешные результаты» и не скрывает неполноту.

Первый релиз экспортирует Markdown/JSON и CSV matrix. DOCX ПСИ и корпоративные шаблоны — P1. Содержание ПСИ в реестре не зависит от наличия DOCX export.

### 14.6. Readiness

Отчёт содержит по scope: agreed requirements, unresolved decisions, stale relations, verified code reachability, applicable executed/pass/fail tests, waivers и unknowns. Итог: ready, not_ready, insufficient_data; основание видно.

Каждый readiness calculation фиксирует baseline_uid, assessment_uid, policies и evidence set. Для неизменяемой baseline новые test runs создают новый assessment, а не модифицируют baseline manifest.

## 15. Архитектура и реализация

### 15.1. Предлагаемый стек

| Слой | Рабочий вариант | Причина |
| --- | --- | --- |
| API/application | Python + FastAPI + Pydantic | Типизированный JSON/OpenAPI, удобные адаптеры для ИИ |
| Persistence | PostgreSQL + SQLAlchemy/Alembic | Транзакции, immutable revisions, relational graph и индексы |
| Jobs | Worker с durable PostgreSQL queue/outbox | Первый релиз без отдельного orchestration cluster |
| UI | React + TypeScript | Типизированные формы, client state и анализ |
| UI styles | Tailwind и согласованная component library | Единообразные карточки/таблицы/формы |
| Graph UI | React Flow либо эквивалент после spike | Локальный граф и взаимодействие с узлами |
| Files | S3-compatible или local object store с backup | Immutable sources/attachments и hash checking |
| Git | Provider-neutral git adapter/CLI в worker | Проверяемые objects, refs, diffs, reachability |
| AI access | REST SDK + MCP adapter + Claude skill pack | Общая доменная логика для разных клиентов |
| Delivery | Docker Compose | Простое локальное/self-hosted развёртывание |

Конкретные версии фиксируются lockfiles при начале реализации. Это предлагаемый стек, не пользовательское обязательное ограничение. Neo4j, vector DB, Temporal, Kafka и собственный LLM gateway не требуются для первого релиза.

### 15.2. Границы модулей

- project-access: Project, memberships, tokens, capabilities.
- knowledge-registry: Artifact, Revision, Schema, aliases, sources.
- traceability: Relation, paths, obligations, coverage.
- change-control: ChangeSet, validation, impact, review, policy.
- ai-context: bundles, AgentRun, MCP/SDK contracts.
- repository-integration: Git, code refs, commits, CI manifests.
- verification: TEST, PSI, TestRun, Evidence, readiness.
- snapshots-reporting: Baseline, exports, assessments.
- operations: jobs, outbox, audit, retention, backup.

Это модульный монолит: один API-процесс и worker, одна транзакционная БД. Наличие модулей не означает отдельные микросервисы.

### 15.3. Поток команды

UI/MCP/CLI → authentication → command schema → authorization/policy → application service → transaction/revisions/audit/outbox → worker analysis/integrations → results/notifications.

Сервер не обращается к LLM внутри apply-транзакции. Semantic analysis — отдельный job либо findings от внешнего агента. В API response видно, какие проверки уже выполнены и какие pending.

### 15.4. Индексы и выборки

Индексы: artifact(project,type,status), unique display_id; alias namespace+external_id; relation(from/to,type,status); source(hash); commit(repo,format,oid); code_ref(repo,oid,path); findings(project,status,subject); jobs(state,available_at).

Graph traversal: adjacency в PostgreSQL, bounded recursive queries или traversal worker. Arbitrary unbounded paths запрещены. Векторный поиск можно добавить в P1 как индекс, не источник canonical links.

### 15.5. Baseline snapshot

Baseline manifest хранит выбранные artifact revision IDs, relation revision IDs, schemas/policies/rule versions, source refs, repo commit OIDs и scope. Snapshot создаётся из consistent graph_revision.

К baseline можно позднее прикреплять assessments/runs отдельными append-only записями; её manifest/hash не меняется. Для исторического просмотра relation confirmation берётся из pinned revision, а актуальность отображается относительно выбранного assessment mode.

### 15.6. Безопасность и isolation

Project-level access применяется к search, paths, exports, source bytes и Git refs. Отсутствие доступа не должно раскрывать title закрытого узла через path.

Uploaded bytes имеют limits и MIME validation. Connector запускает фиксированные Git операции без shell interpolation полей. В credentials storage secrets шифруются; responses/logs их исключают.

API keys ограничены project/capability и сроком, отзыв немедленный. UI auth использует защищённую session; request IDs и on_behalf_of сохраняются. Агент не может присвоить себе human issuer.

Произвольное исполнение проверок и кода на сервере не входит в P0. CI выполняет тесты во внешней среде и передаёт results.

UI присутствует с E2 и развивается вместе с API. Скиллы создаются вместе со своими server operations; не откладываются «после всего backend».

### 18.2. Что блокирует ключевые функции

| Функция | Обязательные prerequisites |
| --- | --- |
| Import accepted spec | Source identity, schema, temp refs, idempotency, aliases, ChangeSet |
| Impact highlighting | Typed relations, revisions, field diff, applicability, bounded traversal |
| Работа Claude с текущими знаниями | Context manifest, source refs, freshness, capabilities, MCP |
| Canonical apply | Transaction, expected revisions, policy, validation, audit/outbox |
| Trace до commit | Repo identity, full OID verification, code refs, pinned requirement versions |
| Verification/readiness | Obligations, TEST revisions, evidence identity, baseline target code |
| ПСИ | Проверяемые criteria/НФТ и coverage gaps; LLM не исправляет отсутствие данных автоматически |
| Исторический replay | Immutable sources/revisions/manifests и backup объектов |

Не следует начинать с графического графа, embeddings или автоматической генерации ADR до принятия семантики сущностей и связей. Они опираются на canonical model.

### 18.3. Минимальный пилот

Один пример проекта с 2 BR, 3 US, 6 FR, 2 NFR, 2 CON, 3 ADR, 3 CMP, 5 TASK, 8 TEST и настоящим demo Git repo.

Пилот включает импорт → UI review → изменение NFR → impact/review → Claude context → code commit → CI evidence → baseline → PSI export. Первый удобный прототип E2/E3 не называется завершённым P0 до Git/verification частей.

### 18.4. Definition of Done для фичи сервиса

Связаны PTH-US/PTH-FR; реализован API контракт и authorization; есть UI/skill path где применимо; change/history/provenance сохранены; meaningful negative/acceptance tests выполнены; документация обновлена; implementation commits связаны с IDs этой спеки.

Сервис должен демонстрировать собственную трассировку на своём проекте после достижения E4. До E4 применяется временный manifest в репозитории, затем импортируется без потери исходных SHA.

## 19. Метрики продукта и качества

### 19.1. Продуктовые

- Время от принятого текста до первого проверенного реестра.
- Доля импортов, завершённых без ручного исправления ID/связей.
- Время выявления и закрытия последствий изменения.
- Доля задач ИИ с записанным актуальным ContextBundle.
- Доля implementation commits с проверенной трассировкой и pinned requirement revision.
- Время подготовки проекта ПСИ и число оставшихся неизвестных условий.
- Число обнаруженных расхождений до merge/приёмки.

### 19.2. Качество реестра

- Source disposition coverage и отдельно human-reviewed extraction recall на sample.
- Доля confirmed связей с проверяемым основанием.
- Coverage ratios по obligation type; denominator и unknown applicability видны.
- Needs_review/stale age и время их разрешения.
- Precision impact: доля действительно требовавших действий объектов среди отмеченных. Recall оценивается на размеченных сценариях, а не из production counts.
- Доля false semantic findings и accepted/rejected proposed links.
- Orphan/unreachable code references, incomplete manifests, revision mismatch.
- Evidence freshness и доля agent_claimed против trusted_ci.

### 19.3. Эксплуатационные

Latency/error rate, conflicts, job duration/retries, queue/outbox backlog, failed Git sync, restore success, storage growth, bytes/tokens per bundle и LLM cost metadata при наличии.

Нельзя оптимизировать «количество созданных требований», «количество связей» или общий coverage % без качества и scope: ИИ может искусственно увеличить их, не улучшая проверяемость.
